# ai-agent-runner design, v0

**Goal.** From my laptop, start an AI agent in its own Firecracker microVM on my KVM box. I drive it from local Claude Code over MCP or step into its shell over SSH, and it keeps its files between runs, like fly.io Sprites.

## ★ Approach: SSH is the control plane, every VM is a fork

```
laptop                                        KVM host (tailnet only)
Claude Code ── ssh kvm-host runner mcp ──┐    runner: one Rust binary
runner CLI  ── ssh -t kvm-host runner … ─┴──▶ /var/lib/runner/vms/<vm>/  state, no database
                                              firecracker@<vm>.service   systemd
                                              vsock ─▶ small guest agent in the VM
```

- **No daemon, no API, no open ports.** Local Claude Code registers `ssh kvm-host runner mcp` as a stdio MCP server, and the CLI is `ssh -t kvm-host runner …`. `runner proxy`, the one command the laptop runs itself, is `ssh -L` to a VM's address through the host, running `runner hold` there so the VM counts as used while it's open. SSH keys are the auth and the tailnet is the network. MCP tools and CLI commands call the same functions.
- **The filesystem is the database.** Each VM is a directory with its disk generations and a `history` whose last line is the current one.
- **Every VM is a fork.** Disks are reflink copies on XFS or btrfs, with a sparse full copy elsewhere. An image is a VM you stopped changing; `base` is the one you fork most. A run clones the current disk into a new generation that only a clean finish commits, so a crash rolls back for free and `undo` steps back one. Every commit then deletes old generations, keeping my checkpoints, the newest 20 that runs and the agent made, and five more, undo's way back first; `runner gc` does the same by hand, skipping a VM that's up. A running VM's checkpoint syncs the guest, pauses it through Firecracker's API, copies the disk it runs, and resumes it.
- **One run per VM.** The process running a VM holds an flock on it, which the kernel drops if that process dies. In M2 that process is the VM's systemd unit.
- **Runs are detached.** `run` starts `claude -p` in the VM and returns a run id at once; `output` reads its log by offset. A process of its own drives each run, in a session of its own, holding the VM's run lock, so a closed laptop or a dropped SSH connection can't kill a run, and the log is on the host, in the VM's directory. A run on a stopped VM boots it and shuts it down at the end, committing only a clean exit; one on a running VM checkpoints it and joins it, and never restarts it, since that would end its sessions: a failed run's result names the checkpoint to restore by hand. Once the VM is down, the run's own process measures what changed between the generation it booted and the one it booted from, reading both disks in userspace, and writes that result before it says the run is over.
- **Best of N is N forks.** `runner run dev --n 3` forks dev three times and starts an ordinary run in each, so a try is a VM and a run like any other, and dev is never touched: a running or sleeping dev is checkpointed as a joined run's is, and the tries fork that (`src/best.rs`). It holds dev's run lock while it forks, checks every name, the host's MemAvailable less 1 GiB against N times dev's memory, and that no earlier batch's tries are still VMs before it makes anything, and records the batch in dev's `tries.json` for `tries` and `keep` to read. `runner tries` and MCP's `list_tries` read it with each try's run and result into one view (`best::standing`): a try whose fork or run isn't on dev's host any more shows as gone, and nothing else is stored. Names stay one per name across hosts: the laptop's `runner run --n` and MCP's `run_best_of` refuse a try's name another host has, and dev's host refuses its own. `runner keep dev-2` copies dev-2's current disk under dev-2's lock, so it can't boot meanwhile, onto dev with `Store::stage_disk`, and puts it on top of dev's history as a restore's copy goes (`checkpoint::put_disk`, which stops a running dev and starts it after), then deletes every try and dev's record of the batch. A try still at generation 0, the copy of dev's disk it forked, is refused, as is one whose run is going or that's up but for a run's own boot, which the cancel shuts down; every check comes before the first change.
- **A fixed address per VM.** A slot picked at create gives each VM a /30 of the host's range (`/etc/runner/net`, which `host/install.sh` writes and NATs; default 172.16.0.0/16) and a tap named for it. The guest gets its address, gateway and DNS from the kernel's `ip=` argument, and the image links `/etc/resolv.conf` to `/proc/net/pnp` to use them. Its one DNS server is its gateway, where its boot answers on port 53 and passes each query on to the host's resolvers (`src/dns.rs`). A VM with a list of names in its config gets answers only for those names and the names under them, plus api.anthropic.com, and REFUSED for the rest, unasked; each allowed answer's addresses are handed on before the guest gets it, for the host's rules to open (`src/fence.rs`). Those rules send a listed VM's tap to a chain of its own, which lets through what's open already and what goes to an address paired with the tap, and drops the rest, another resolver's port 53 included; the private ranges are dropped before it. Its boot puts the tap in the rules' set of listed taps before the tap is made, and each answer's addresses in beside it for the answer's TTL, but at least 10 minutes, since programs keep answers past it; the rules follow the list as the DNS reads it, a name taken off taking the pairs out, and each of boot's looks puts the tap back after a firewall reload empties the sets. That leaves a listed VM unheld for up to 10 seconds after a reload, rather than a set of open taps that would cut every VM off at each one. A boot that can't bind port 53 gives an unlisted guest the host's resolvers instead; a listed VM doesn't boot, nor does one whose tap can't go in the rules. Beyond that, the runner only adds and removes taps, and listed ones' places in the rules.
- **A list of names is set by hand.** `runner net <vm> allow|deny|list|open` changes the list in the VM's config (`Store::allow`, `deny`, `allow_all`), one command at a time under the VM's `config.lock`, and a running VM's boot takes it within a second. MCP only reads it (`vm_allowlist`, marked read-only), as with credentials, which no MCP tool sets: a local Claude Code reads VMs' output, so it's what an agent in one would talk into widening its list. In the VM, `/.runner/llm.txt` says a REFUSED name is off the owner's list, and to ask.
- **Into the VM over vsock.** The host reaches a small guest agent through Firecracker's vsock socket, so the guest needs no sshd and no keys. `runner shell <vm>` is SSH to the host, then a terminal over vsock.
- **Services are systemd units in the guest.** `runner service add` writes `/etc/systemd/system/runner-svc-<name>.service` over the guest protocol, as root, and enables it, so it runs from every boot with `Restart=always`. The disk keeps the unit; no state about it is on the host.
- **A rebase is a fork of base with the VM's own copied in.** `runner rebase <vm>` (`src/rebase.rs`) makes a new generation of a stopped VM from a copy of base's current disk, then copies in the VM's `/home`, `/root`, `/etc/machine-id` and the runner's services (units and their `*.wants` links), then base's Claude Code over that `/home`, all file by file with `src/graft.rs`: the VM's disk is read with ext4-view, never mounted, and only debugfs writes the copy of base, so debugfs never opens a disk a guest wrote. That's why base's current generation has to be one an import made. It's under the VM's lock, so refused while the VM is up, as `undo` is, and goes on top of history, so `undo` goes back; a failed one leaves nothing. What's kept is a list in the code, not a setting. Apt packages, users added since, crontabs and `/var` are lost, and the output says so. Copying inside a VM booted from base with the old disk attached would keep hard links and xattrs, but every test would need KVM.
- **Sleep keeps the boot.** `runner sleep` has the VM's boot pause it, write a Firecracker snapshot of its memory and devices into its directory, and stop Firecracker; the boot stays up, holding the VM's lock, tap and guest sockets, so `wake` only starts a fresh Firecracker to load the snapshot, then sets the guest's clock (`src/sleep.rs`). The snapshot runs on the boot's own uncommitted disk, so only that boot can wake it: a stop wakes the VM to shut down cleanly, and a restore stops it first. A host shutdown is the one exception: `runner-park.service`, which every VM's unit is ordered before, so it stops first, has each sleeping VM's boot sync its snapshot and disk, note them parked and end without committing. The next boot gets that same run back, on that disk, and loads the snapshot rather than booting a fresh copy, unnoting it first, so a boot that dies after the load can't resume it onto a disk written since; one whose load fails boots the last committed disk and keeps the parked one. Until then nothing holds the VM's lock, so the store refuses a parked VM as busy itself.
- **Sleep when idle.** Each command that needs a VM's guest, or would hold the VM as a sleep does (`run`, `checkpoint`, `restore`, `export`), holds its use lock, shared, from before it looks at the VM until it's done, and touches the lock's file at each end. So does `runner hold`, the command an open `runner proxy` runs on the host, until its SSH connection closes, which it sees as its stdout hanging up. Every 10 seconds the boot looks: the lock held or touched, a run going, or a terminal on a tmux session in the guest (asked last, of runner-guest, as root) count as use. Once none has been seen for the VM's idle time, 10 minutes unless `runner idle` says otherwise, the boot puts it to sleep holding the lock exclusive, so a command that comes then waits, sees it sleeping, and wakes it (`src/idle.rs`).
- **The host stops itself when idle.** Once every VM on it has been stopped or asleep, no one but runner logged in, and no runner command at work for the host's idle time, it powers itself off, and EC2 stops the instance, so only its disks cost (`src/power.rs`). Every command and MCP call holds `<root>/busy.lock` shared while it works and touches it as it lets go; a look every minute, `runner host-idle` from `runner-host-idle.timer`, counts a held lock, a VM up or a login as use and touches the lock then, so its mtime is the last use, and the idle time counts from that or the host's boot, whichever is later. runner's own SSH sessions don't count, so a `runner mcp` left open on the laptop doesn't keep it up. The look says why in its journal, then powers off as runner through logind, which a polkit rule allows and nothing more; the shutdown parks each sleeping VM and shuts the rest down cleanly, as any does. The idle time is `/etc/runner/host-idle`, which `host/install.sh` writes from `RUNNER_HOST_IDLE`: never by default, and an hour on a host `client/aws.sh setup` made, since runner stops only hosts `aws.sh up` made. `aws.sh up` launches the host to stop at a power-off, not terminate, and `start` sets that back on a host set to terminate.
- **A command starts its stopped host.** Before a command goes to a host, the laptop's `client/runner` asks it over BatchMode SSH whether it answers, unless this run has reached it already (a VM's host checked with `runner ip`, or a list), or there's no AWS CLI or `aws.sh` beside it, which `client/install.sh` puts there. Only a host that doesn't answer is looked up, by its name, with `aws.sh state` (among instances `up` made), and only one AWS has stopped, stopping or pending is started, by `aws.sh start` for that host alone, its output on stderr so MCP's stdout stays JSON-RPC; then it waits for SSH, a few minutes at most, and the command goes, by `exec ssh` as ever, once. Asking first, not going by the command's exit, is what keeps a command that ran from running twice: ssh exits 255 for one that couldn't connect, for one that couldn't run, and for a session dropped as its host stopped, as `aws.sh stop` or the host's idle power-off does under a `runner mcp` left open. A command for one host starts it, `move`'s target included; one that asks every host starts none and names the stopped ones.
- **A URL per VM, on the tailnet only.** The VM's boot listens on the host's Tailscale address at 10000 plus the VM's slot, the only port the runner opens, and takes connections only from Tailscale's range, so not from the LAN or another VM. Each connection holds the use lock, has the boot's loop wake the VM if it's asleep, waits for the guest to accept on port 8080 (or what `runner url --port` set), and passes TCP both ways (`src/url.rs`). The setting is in the VM's config, which the boot reads every second.
- **An export is a tar.** `runner export` streams a VM to stdout as a tar GNU tar reads: a manifest first, with a format version, the VM's config, its allowlist's names and its checkpoints' ids, times and comments, then the current disk and each of the owner's checkpoints as GNU sparse files holding only the extents SEEK_DATA finds (`src/export.rs`, written with the tar crate). The store opens every disk under the VM's lock, a running VM's under its freezer, and lets go before a byte goes out: committed generations are never written again, so the VM can start, or be deleted, while it streams. The sleep snapshot, which holds the guest's memory and credentials, is never in it. A running VM's current disk is a copy made as its checkpoint is (sync, pause, copy, resume), unlinked once open (`Freezer::open_copy`), so it carries on and nothing is left; a sleeping one is woken first, and one with a run going is refused, since a run's disk may roll back. Backups leave the host through the laptop, so the host holds no cloud credentials. `runner import` brings one back as a new VM, reading it in Rust with the tar crate, never tar the program: only the entries the manifest names, in order, each a plain or sparse file, written sparse under the store's own names, then tar's end (`src/import.rs`). It builds the VM under a staging name and renames it in last, as a create does, so a stream cut short or refused leaves nothing. The checkpoints keep their ids, times and comments; the slot is new, and the allowlist is the default, as for a fork.
- **Several hosts, from the laptop.** The CLI asks the hosts from the laptop: `client/runner` lists them in `~/.config/runner/hosts` and asks them all at once, over BatchMode SSH with a short ConnectTimeout, for `runner list` and `runner hosts` (each host's VMs, the ones up, and MemAvailable). A command naming a VM goes to its host, from a cache of the last lists that `runner ip <vm>` on that host checks first, with no stdin, so a stale entry costs one round of asks and never a command run twice or stdin lost. `create` places by free memory, and names are unique across hosts, base aside. MCP goes to the first host, which reaches the rest (MCP across hosts).
- **Hosts trust each other, and nothing more.** Each host's runner user has a key of its own, which `host/install.sh` makes. `runner hosts add` on the laptop reads each host's public key, takes it only if it's a bare ed25519 key, so a host can't slip options or another line in, and writes it into every other host's `~runner/.ssh/authorized_keys` behind `from=` Tailscale's ranges, `restrict` and `command="/usr/local/bin/runner peer"`, with the host's name last, which `hosts add` and `hosts rm` go by. The laptop is the one place that knows every host, so it alone hands out keys; no host vouches for another. sshd runs `runner peer` for that key whatever the other host asks, and leaves what it asked in SSH_ORIGINAL_COMMAND. `runner peer` takes it only as words of the characters VM names and flags use, so nothing in it is a shell's, and only `runner mcp` or `runner import <vm> -` with their own flags, which clap then parses and this process runs, on this host's root (`src/peers.rs`). It's what MCP across hosts goes through, and what a move streams through. A host that's taken over gets every host's VMs, as MCP gives them, and through `import --creds` a VM of its own that a host hands any credential it holds, so its tokens too; but no shell, terminal, forwarding or other command on another host. `--creds` and `--no-creds` are there for a move, which keeps a VM's allowlist. The laptop's key is still the only one that logs in.
- **A move is an export into an import, host to host.** `runner move <vm> <host>` runs on the VM's host (`src/moves.rs`): holding the VM's run lock, it asks the other host's MCP, as a peer's (peers::Remote), whether it has a VM by that name, stops the VM if it's up, then, holding the VM's lock so nothing starts it, streams its export into `ssh <host> runner import <vm> - --creds …` with its own key, through the other host's `runner peer`. It deletes its copy only once that import exits 0, and starts the VM there through MCP if it was up. The import builds aside and renames in last, so a failed or cut-off one leaves nothing there and the VM here as it was; if ssh fails after the whole stream went, the other host's list says whether it took it, and if that host doesn't answer, the VM stays here and the error says both hosts may have it. A stop that doesn't commit, a kill or a crash, ends the move with the VM here, stopped, since its current disk is older than what it ran. The move runs on one thread with a runtime of its own, ignoring SIGINT and SIGHUP from the CLI, so neither a terminal nor an MCP session going away leaves it half done. A VM that's up is stopped and started again, ending its processes, rather than refused as gc refuses one, and its runs stay behind; both are defaults to revisit. `move_vm` goes to the VM's host like any call naming a VM, with its `host` rewritten as listed, since a peer's own MCP has no peers to name it by.
- **MCP across hosts, through the first.** The laptop's `runner mcp` stays one SSH session, to the first host, and passes the rest of the hosts file as `--peer`s, and the first host's own name as listed, so MCP names every host as `runner list` does. That host's runner opens one `ssh <peer> runner mcp` per peer on first use, with its own key alone, which the peer's forced command lets through as `runner mcp` (Hosts trust each other), and keeps it; rmcp's client side carries the calls. `list_vms` and `list_hosts` ask every peer at once and name the ones that don't answer; `create_vm` places as the laptop's `create` does; any other call naming a VM or a run goes, as it came, to the host that has the VM, found by asking this host first, then the peer it was last listed or made on, then every peer's `list_vms`, so where VMs are is only ever a hint, checked before it's used: it keeps a VM on a live peer from waiting on a host that's down, and names a VM's host when that host stops answering. Lists wait 20 seconds on a peer; calls wait as long as the tool does. A peer's own MCP takes no peers (`runner peer` refuses `--peer`), so a call is forwarded at most once and two hosts never forward to each other. A call isn't sent again when a session drops under it, since it may have run there. The alternative, the laptop's Rust runner as the MCP server with a session per host, needs no keys between hosts but a Mac build; this keeps the laptop to `client/runner`.
- **Out of the VM, to its own boot.** The agent checkpoints, lists and restores its own VM with `runner-guest checkpoint`, `checkpoints` and `restore`, calls over vsock that the VM's `runner boot` serves (`src/calls.rs`). No call names a VM, so a guest can't reach another. Its checkpoints are capped at 10 an hour, and gc keeps the newest 20 of its and runs' together. A restore reboots the VM onto the copy: boot commits at the clean shutdown, then exits with a status the unit restarts on. `/.runner/llm.txt` in the base image tells the agent all this.

## Guards

- Only my agents; the host is reachable only over the tailnet. runner starts and stops only hosts `client/aws.sh up` made, and never makes one.
- Credentials come in per boot and never land on a VM's disk, so a forked disk holds no keys.
- A run's result keeps what the runner measured apart from what the agent wrote, which is marked untrusted.

## Credentials

- The host holds `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`) or `ANTHROPIC_API_KEY`, and optionally `GH_TOKEN`. Each comes from a systemd credential of the same name (`LoadCredential=` in `firecracker@.service`, read from `/etc/credstore/<name>`), or else the environment, never from a file in the repo or a VM's directory.
- Each VM has an allowlist of credential names in its directory: `claude` by default, `github` only when `runner creds <vm> claude github` adds it. A fork starts from the default. No MCP tool sets it; `runner import --creds` does, which a peer host may run (Hosts trust each other).
- `runner-guest` asks for them each time it starts, before it takes a command: it connects to the host (CID 2) on vsock port 10023, which Firecracker passes on to `vsock.sock_10023` in the VM's directory, where `runner boot` hands it the allowed ones (`creds::Keyring`). So no command runs without them, and a restarted guest gets them again. A guest the host can't answer runs without.
- The guest keeps them in memory, takes only those variables, and sets exactly them in each command's environment, sessions and runs included (`Keyring::apply`), last, so a request can't add or change one. Its unit sets `LimitCORE=0`, so no core dump writes one to the disk, and the base image sets up no swap.
- The host refuses a request that sets one, from `runner exec -e`, MCP's exec or any other (`creds::refuse`), with an error saying credentials reach a VM only through `runner creds`. It names the variable, never its value.
- A sleeping VM's snapshot is its memory, so it holds them: in `<vm>/snapshot/`, which only the runner user can read, until the VM wakes, or, if its boot was killed asleep, until it next boots or is deleted. It's no disk's, so forks and checkpoints still hold none.
- Boot notes which ones the guest took in `<vm>/handed`, names only, and `runner status` shows them while the VM is up: `running  creds claude`.

## Assumptions (correct these)

- The host is a Linux machine of yours with KVM, on your tailnet, with XFS or btrfs under `/var/lib/runner`.
- Claude Code is the first agent, installed in the base image.
